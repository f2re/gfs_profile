# 🕒 Автоматическая отправка прогнозов

`/schedule` открывает менеджер автоматических отправок. На одного Telegram-пользователя допускается не более двух активных расписаний.

Поддерживаются точечные продукты:

- вертикальный профиль GFS;
- аэрологическая диаграмма;
- windgram;
- cloudgram;
- одиночная карта, серия карт или анимация;
- метеограмма PNG, DOCX или PDF, включая ансамблевые системы.

Маршрутный профиль намеренно не включён: его время валидности зависит от времени старта и движения по маршруту, поэтому для регулярной автоматической отправки требуется отдельная семантика.

## Пользовательский сценарий

```text
/start → 🕒 Расписания
или /schedule
→ ➕ Новое расписание
→ продукт
→ обычный мастер продукта: город + все параметры
→ 🕒 Далее: расписание
→ частота
→ местное время города
→ подтверждение
```

Примеры:

```text
Пятигорск → Карта → Анимация +0…+24 ч, шаг 3 ч
→ Каждые 3 дня → 06:00 → Europe/Moscow

Мурманск → Метеограмма → GEFS → 5 суток → PDF
→ Каждый день → 13:00 → Europe/Moscow
```

После каждой автоматической отправки бот показывает две компактные кнопки: `⚙️ Расписание` и `🗑 Отменить`.

## Местное время

После выбора города бот запрашивает часовой пояс точки через Open-Meteo `timezone=auto` и сохраняет IANA-имя (`Europe/Moscow`, `Europe/London` и т. п.). Если автоматическое определение недоступно, пользователь выбирает/вводит часовой пояс вручную.

Повтор задаётся в календарных местных сутках. Поэтому время `06:00` остаётся `06:00` после сезонного перевода часов. Для несуществующего времени в момент весеннего перевода используется первая реально существующая локальная минута после перехода; для повторяющегося осеннего часа — первое вхождение.

Первый запуск — ближайшее будущее наступление выбранного времени, далее через N местных календарных дней.

## Исполнение и восстановление после перезапуска

Отдельный Redis/Celery/systemd timer не нужен. Один фоновый `asyncio`-цикл запускается вместе с существующим long-polling Telegram-процессом и завершается вместе с ним.

Расписания хранятся атомарно в:

```text
.cache_gfs/telegram_schedules.json
```

Каталог `.cache_gfs/` уже сохраняется штатным deploy, поэтому расписания переживают обновление приложения.

Перед запуском срок сразу переносится на следующий календарный период. Это исключает двойную отправку при аварии процесса после генерации. После длительного простоя старше `TELEGRAM_SCHEDULE_MAX_LATE_MINUTES` пропущенная продукция не строится задним числом: срок переносится на ближайший будущий.

При каждом запуске выбирается актуальный опубликованный цикл/модельный прогноз. Цикл, существовавший в момент создания расписания, не фиксируется.

## Настройки

```text
TELEGRAM_SCHEDULE_FILE=.cache_gfs/telegram_schedules.json
TELEGRAM_SCHEDULE_POLL_SECONDS=30
TELEGRAM_SCHEDULE_MAX_LATE_MINUTES=180
TELEGRAM_SCHEDULE_TIMEZONE_TIMEOUT=10
MAX_CONCURRENT_SCHEDULED=1
```

`MAX_CONCURRENT_SCHEDULED=1` намеренно сохраняет нагрузку слабого сервера предсказуемой; собственные GFS/метеограммные семафоры продолжают действовать.
