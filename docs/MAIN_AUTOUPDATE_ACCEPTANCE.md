# Приёмка выпуска через main и автоматического обновления меню

Дата: 18 ноября 2026 года.

## Решение и границы проверки

Изменения приняты для выпуска обычным слиянием `telegram-bot` в `main` с
сохранением истории. `main` становится production-источником systemd-обновлятора;
рабочая ветка разработки остаётся `telegram-bot`. В выпуск входит ранее
реализованный раздел `/icing`.

Проверены код обновлятора, установщика, деплоя, регистрация команд и переход
старой установки на новый канал. Реальные systemd-службы пользовательского
сервера и внешние API его ботов в этой приёмке не изменялись. Состояние
конкретного сервера подтверждается его журналом, `/ready` и `.install-state`.

## Выявленные дефекты и исправления

| Дефект | Исправление |
|---|---|
| Updater и установщик следили за `telegram-bot` | Default production branch — `main`; развитие и выпуск разделены |
| Старый unit сохраняет `AUTO_UPDATE_BRANCH=telegram-bot` | Миграция через сохранённый `tracking_branch=main` после подтверждённого выпуска; ручное изменение unit не требуется |
| Можно было перейти на существующий, но ещё старый main | Проверяется ancestry свежей legacy-ветки и установленного SHA; до слияния миграция откладывается |
| Нулевой exit deploy принимался без проверки установленной версии | Требуются `deploy_status=complete`, полный точный `source_rev` и пустой `pending_source_rev` |
| Ошибка регистрации Telegram-команд игнорировалась | Общий CLI Telegram/MAX возвращает ненулевой код при ошибке включённой платформы |
| Нативные команды MAX не обновлялись | `PATCH /me/commands`, затем проверка `BotInfo.commands` через `GET /me` |
| Регистрация webhook могла вернуть 0 при частичной ошибке | Скрипты вызывают CLI с `--strict` |
| HTTP 200 `/ready` допускал неработающую включённую платформу | Общий probe проверяет JSON и готовность всех включённых платформ; `degraded` отклоняется |
| `--no-restart` мог публиковать меню для старого процесса | Меню и webhook откладываются; установка получает статус `partial` |
| Пропуск обязательного этапа подтверждал новую версию | Старый подтверждённый SHA сохраняется, кандидат записывается в `pending_source_rev` |
| Перезапуск повторным установщиком не гарантировался | После `enable` вызывается `restart`, затем проверяется готовность |
| Ошибки `source`, `cd`, `daemon-reload` могли поглощаться | Явная остановка и исполняемые регрессионные проверки |
| Запись `.install-state` могла оборвать прежнее состояние | Запись во временный файл и атомарная замена после всех этапов |
| Root-таймер мог получить `unknown` SHA из пользовательского checkout | Доверие Git задаётся только для конкретной команды и каталога; проверяются `HEAD^{commit}` и полный SHA до изменения установки |
| Runtime не учитывал старое имя `BOT_TOKEN`, хотя Telegram и CLI его поддерживали | Общая проверка конфигурации учитывает alias; явное `TELEGRAM_ENABLED=0` сохраняет приоритет |

Отключённые платформы не блокируют выпуск. В Telegram-only режиме CLI меню
получает `--telegram`, даже если сохранён старый MAX-токен.

## Проверенная цепочка

1. Таймер получает свежий `origin/main` и берёт lock.
2. Сверяются checkout и фактически установленный SHA.
3. Штатный deploy сохраняет конфигурацию/кэш и синхронизирует приложение.
4. Выполняются зависимости, unit tests и preflight.
5. Перезапускается один systemd-процесс.
6. Проверяются runtime и все включённые платформы.
7. Команды Telegram/MAX записываются и считываются обратно через API.
8. Webhook MAX/VK регистрируются со строгой проверкой результата.
9. Полный SHA и `deploy_status=complete` записываются атомарно.
10. Updater сверяет установленный SHA; при отказе запускает штатный откат.

Изоляция работающих платформ внутри runtime сохранена. Строгость применяется
к подтверждению полного выпуска. Деплой использует перезапуск одного процесса,
поэтому краткая пауза обслуживания возможна.

## Автоматические проверки

Финальный полный прогон в базовом окружении `requirements.txt`:

```text
Ran 682 tests in 46.314s
OK (skipped=2)
```

Пропуски относятся только к прежним интеграционным тестам необязательных
BigQuery/Zarr SDK WeatherNext. Проверки GFS, обледенения, updater, меню и деплоя
выполнены без пропусков. `runtime_check.py`, shell syntax и `git diff --check`
пройдены.

Отдельно приняты:

- 12 тестов updater, включая настоящие временные git remote, rollback,
  блокировки, повтор, shallow clone и перенос канала;
- 44 теста deploy/install/readiness/revision, включая исполняемые shell-функции,
  сбои этапов, атомарность state и отказ при HTTP 200 с degraded-платформой;
- регистрация Telegram/MAX, выбор включённых платформ, сверка команд,
  отсутствие публикации WeatherNext при выключенном feature flag;
- независимый повтор приёмки установщика и readiness другим агентом.

Указанные группы входят в общий набор; складывать их количества не следует.

Ошибка владельца checkout воспроизведена настоящим Git с его regression-флагом
`GIT_TEST_ASSUME_DIFFERENT_OWNER=1`. Обычный вызов отклонён с `dubious ownership`;
исправленные функции обоих скриптов прочитали точный SHA. Глобальный Git config
остался неизменным. Отсутствующий HEAD и ответ `unknown` не изменили прежний
state. Три проверки старого `BOT_TOKEN` подтвердили автоматическое и явное
включение Telegram, а также приоритет явного выключения.

## Проверка первого обновления историческим updater

Отдельный одноразовый эксперимент использовал именно исходный скрипт:

```bash
git show 8f78d3e:auto_update_telegram_bot.sh
```

Созданы изолированные старый checkout и локальный remote. В окружении старого
unit установлено `AUTO_UPDATE_BRANCH=telegram-bot`, нового pin-параметра нет.
Deploy-граница заменена stub, записывающим фактический SHA; настоящие systemd
и API не вызываются.

| Запуск | Что выполнено | Результат | Число deploy |
|---|---|---|---:|
| 1 | Старый entrypoint получил новый updater из legacy-ветки | `deployed`, checkout `telegram-bot` | 1 |
| 2 | Новый entrypoint увидел опубликованный merge в main | `deployed`, checkout `main` | 2 |
| 3 | Повторная проверка без новых изменений | `up-to-date`, checkout `main` | 2 |

После второго и третьего запусков:

```text
requested_branch=telegram-bot
effective_branch=main
tracking_branch=main
```

Таким образом, отдельно проверен первый переход через старый скрипт, а не
только работа нового updater на заранее подготовленном checkout. Новые
неопубликованные development-коммиты после миграции не попадают в production.
Явно закреплённые тестовые ветки сохраняются.

## Живые проверки GFS

Обе обязательные команды завершились с кодом 0:

```bash
python -m gfs_core --lat 45.0355 --lon 38.9753 --lead 24
python -m gfs_core --lat 55.75 --lon 37.62 --lead 384
```

Для +24 выбран цикл 18.11.2026 00 UTC, valid 19.11.2026 00 UTC.
Для +384 выбран опубликованный цикл 17.11.2026 18 UTC,
valid 03.12.2026 18 UTC.

## Что подтверждает состояние рабочего сервера

Публикация Git-коммита сама по себе не запускает отсутствующий или отключённый
таймер на удалённом компьютере. Для уже включённого штатного legacy-таймера
переход выполняется автоматически после получения этого выпуска.

Проверяются active/enabled таймер, эффективная ветка `main`, совпадение SHA
в `.install-state` и `origin/main`, полный статус деплоя, готовность runtime и
синхронизация меню. Команды диагностики и первичной установки:
[DEPLOY.md](../DEPLOY.md).

Новый `/start` формирует актуальные кнопки, включая «Обледенение». Старые
inline-сообщения не переписываются массово. Индивидуальные Telegram command
scopes, созданные вне проекта для конкретных чатов, не перечисляются глобальным
Bot API. Свежая MAX-only установка без Telegram-токена не входит в область
этой приёмки; обновление существующей такой установки проверено на уровне
контрактов и изолированных сценариев развёртывания.
